# S3

## S3 Security (Resource Policies and ACLs)

- s3 is pvt by default (only root user can access)
- resource policies (bucket policies)
  - determine who can access
  - can allow/deny different accounts
  - can allow/deny anonymous principles
  - _(specifies both resource and principle)_
  - only one resource policy per resource
- ACLs - access control lists
  - legacy, deprecated (?)
  - AWS prefers you use resource policies
- "block public access" settings
  - launched recently because admins couldn't properly configure the policies, causing data leaks etc
  - so, a blanket failsafe policy to simplify the settings if you don't know much

## AWS KMS (Key Management Service)

- regional and public service
- manage keys for encryption, both symmetric and asymmetric, and do crypto ops
- aws owned and customer owned keys
- every key has a key policy (resource policy)
- keys never leave kms (compliant with FIPS-140-2 L2 standard)
  - keys are stored in encrypted form when on disk. can be in plaintext in memory
- backed by **_physical_** key material
- there's strong role-separation - permissions for managing keys, encryption, decryption, etc are different, and a user may not have all of those
- keys can work on data <4kb in size
  - Data encryption keys (DEKs) are used to bypass this limitation
  - KMS doesn't store DEKs, instead gives it to user to perform crypto ops
- e.g.
  ```bash
  echo "<text to encrypt>" > input.txt

  aws kms encrypt \
      --key-id alias/<Key Alias> \
      --plaintext fileb://input.txt \
      --output text \
      --query CiphertextBlob \
      | base64 --decode > encrypted.enc

  aws kms decrypt \
      --ciphertext-blob fileb://encrypted.enc \
      --output text \
      --query Plaintext | base64 --decode > decrypted.txt
  ```

## S3 Object Encryption (CSE / SSE)

- buckets aren't encrypted, objects are
- CSE vs SSE (both are at rest, as opposed to in-transit encryption)
- AWS has recently made SSE mandatory
- **SSE-C**
  - customer provided key + plaintext object
  - ciphertext object and key hash are stored
  - you trust s3 to discard keys after encryption/decryption
- **SSE-S3** (AES256) — this is default
  - aws s3 managed keys
- **SSE-KMS**

  **_todo: diagram_**
  - kinda best-of-both-worlds (?)
  - created and managed by you, but within kms
  - using KMS, S3-SSE creates DEKs (using your kms key) to encrypt stuff
  - stores ciphertext object and encrypted DEK
  - Role Separation is the main benefit here
    - so if an s3 admin has no permissions on kms key, he can manage the s3 buckets/objects, but still can't read/decode data

## S3 Bucket Keys

- using single kms key (Bucket Key) instead of generating new DEK per object
  - offloads work from kms to s3
  - cloudtrail events now show the bucket, not the object
- increases scalability and reduces cost
- time limited
- not retroactive, applies to objects uploaded after enabling this
- etag changes (replicating from one bucket to another, uses destination bucket encryption settings)

## S3 Object Storage Classes

- default is "S3 Standard" — objects replicated across atleast 3 AZs
  - 11 9s of durability (99.99999999999%) — meaning, for 10 million objects, 1 object loss per 10,000 years
  - uses MD5 checksums and cyclic redundancy checks to detect and fix data corruption
  - transfer IN is free, OUT is charged
  - HTTPS/1.1 200 OK
  - "milliseconds" first byte latency
- S3 Standard - IA (infrequent access)
  - same as above except
    - storage costs are much cheaper
    - new cost component — retrieval fee (in addition to transfer fee)
    - minimum duration charge of 30 days
    - minimum capacity charge of 128 kb per object
  - should be used for infrequently accessed data
- S3 One Zone - IA (infrequent access)
  - same as above IA, except
    - cheaper storage
    - stored only in 1 AZ, no replication
  - use for non-critical, replaceable data, with infrequent access
- S3 Glacier - Instant retrieval
  - it's like standard IA, but
    - cheaper storage, more expensive retrieval, longer minimum
  - used when need data instantly, but very infrequently, maybe once a quarter or more
- S3 Glacier - Flexible retrieval
  - same as standard IA, but
    - cheaper
    - objects are cold (aren't immediately available)
      - any access requires retrieval process
      - can't be made publicly accessible
      - first byte latency can be of "minutes" or "hours"
  - used for archival data, accessed maybe once a year
- S3 Glacier Deep archive
  - extremely infrequent and slow access
- S3 Intelligent Tiering
  - 5 different storage tiers
    - frequent, infrequent, archive instant, archive, deep archive
  - monitoring and automated migration between tiers, based on access frequency
  - ideal for long-lived data, with changing/unknown usage patterns

## S3 Replication

- 2 types - cross region (CRR), same region (SRR)
- replication config, role for replication (to be assumed by S3)
- same account vs different accounts
  - diff account replication requires a bucket policy
- you can customise options for replication:
  - all objects or a subset
  - storage class
  - ownership
- by default not retroactive, requires versioning
- no events, glacier and deep archive can't be replicated
- delete markers aren't replicated

## Presigned URLs

- to provide external users access to a pvt bucket and its objects, without having to create any identity or credentials. these are time limited.
- note: you can create the URL for an object you don't have access to, or for an object that doesn't exist
- note: the URL has the same permissions as the identity that generated it (reflects any changes realtime)

```

```

## S3 Access Points

- sharing a large bucket across different users/segments, instead of creating different bucket, or making the entire bucket open to all

- each access point has its own resource policy; bucket policy should have matching permissions
- each access point has a unique DNS address
